## 2. Previous Defect

During the initial S2-T4 Final Runtime Evidence Verification on real PostgreSQL:
- **Error Code**: PostgreSQL `42703` (`undefined_column`)
- **Error Message**: `column "target_commitment_id" does not exist`
- **Location**: `CorrectionRequestService.evaluateExpiredObjectionWindows()`
- **Secondary Latent Risk**: `CorrectionRequestService.objectCorrection()` referenced unquoted column identifiers `objection_window_end` and `requested_by_user_id`.
- **Root Cause**: The raw SQL query used unquoted snake_case identifiers (`target_commitment_id`, `requested_change`, `requested_by_user_id`), whereas the physical PostgreSQL table schema generated by Prisma uses quoted camelCase identifiers (`"targetCommitmentId"`, `"requestedChange"`, `"requestedByUserId"`, `"objectionWindowEnd"`). Because unit tests mocked `tx.$queryRaw` with snake_case mock objects, the physical database defect was masked until executed against real PostgreSQL.

## 7. Fallback Accessor Analysis

In Round 3, fallback expressions were introduced in `CorrectionRequestService`:
```typescript
const targetCommitmentId = cr.targetCommitmentId ?? cr.target_commitment_id;
const requestedChangeRaw = cr.requestedChange ?? cr.requested_change;
const requestedByUserId = cr.requestedByUserId ?? cr.requested_by_user_id;
const objectionWindowEnd = cr.objectionWindowEnd ?? cr.objection_window_end;
```

An independent analysis of these accessors confirms:
1. **Object Shape from PostgreSQL**: When executing `SELECT id, status, "targetCommitmentId" ...`, PostgreSQL returns rows with the exact quoted alias `"targetCommitmentId"`. The resulting JavaScript object has key `targetCommitmentId` populated with the UUID string.
2. **Execution Path**: Because `cr.targetCommitmentId` is non-null and defined, the `??` operator evaluates the left-hand side and short-circuits. The right-hand side (`cr.target_commitment_id`) is **never executed** on the real PostgreSQL path.
3. **Cannot Conceal Future SQL Errors**: If a query were reverted to unquoted `target_commitment_id`, PostgreSQL parses the query on the database server and immediately halts execution with error `42703 (undefined_column)`. No result set is returned, and JavaScript never reaches the fallback.
4. **Purpose & Risk Assessment**: The fallback solely preserves backwards compatibility with legacy in-memory unit test fixtures that mock `$queryRaw` returning snake_case keys. It is harmless, unreachable on real PostgreSQL, and does not conceal any defect.
